# Чем проверяется система

Проверок три, и у каждой своя зона. Граница между ними явная: если её не
держать, начинается «покрытие есть, а ошибка на экране».

| Что | Команда | Что ловит |
| --- | --- | --- |
| Тесты бэкенда | `pytest backend/app/tests -q` | Поведение API, права, деньги, разбор заявок, выгрузки |
| Тесты фронтенда | `cd frontend && npm run test` | Чистую логику: арифметику, разбор текста, правила таблицы |
| Прогон в браузере | Playwright, см. ниже | Вёрстку и то, что видно только на живой странице |

Полный набор перед сдачей:

```
pytest backend/app/tests -q
ruff check backend/app backend/scripts
black --check backend/app backend/scripts
cd frontend && npm run test && npm run lint && npm run typecheck && npm run build
```

## Тесты фронтенда

Раннер — vitest, среда `node`, без jsdom: всё покрытое к DOM не обращается.
Появятся тесты компонентов — тогда и ставить jsdom с testing-library, а не
заранее.

Покрыто ровно то, что **уже ломалось** и чего **браузером не увидеть**:

* [`lib/material-text.test.ts`](../frontend/lib/material-text.test.ts) — разбор
  колонки «Цвет». «RAL 9003мм» — это номер цвета, а не 3 миллиметра; на экране
  «003» в графе толщины выглядит так же правдоподобно, как «19», а карты
  раскроя расходятся молча. Этот тест сразу нашёл живую ошибку: кириллическое
  «рал-9003» не распознавалось, и в списке цветов «Рал-9003» и «RAL 9003» жили
  как два разных значения.
* [`lib/cutting-layout.test.ts`](../frontend/lib/cutting-layout.test.ts) —
  укладка и арифметика закупки: отступ 60 мм от левого края, поворот детали
  (разрешён — ложится, запрещён — не размещается вовсе), и главное равенство,
  на котором стоит расчёт материала: `занятая длина + свободная полоса =
  рабочая ширина`. Разъедется — недозакажем материал.
* [`components/forms/lead-parts-table.test.ts`](../frontend/components/forms/lead-parts-table.test.ts)
  — лишняя пустая строка в таблице расчёта. Дословная жалоба заказчика:
  «начинаю вносить редактирование — снова вылезает лишняя строка, приходится
  удалять каждый раз».
* [`lib/keep-scroll.test.ts`](../frontend/lib/keep-scroll.test.ts) — возврат
  прокрутки. Хелпер один раз уже ломался ровно в том случае, ради которого
  написан: на схлопнутом первом кадре он решал, что дошёл, и стирал позицию.

Правило для новых тестов: **тест обязан падать на сломанном коде**. Проверяется
мутацией — ломаешь строку, гоняешь набор, смотришь, что тест покраснел. Четыре
файла выше проверены так: три внесённые поломки уронили шесть тестов.

Отсюда же требование к коду: правило, которое стоит проверять, выносится из
компонента отдельной функцией (`applyRowPatch`, `planRestoreStep`). Не ради
чистоты — иначе его нечем проверить, кроме глаз.

## Прогон в браузере

Вёрстку и живые страницы гоняем Playwright'ом через установленный Edge
(`channel="msedge"`), скрипты лежат в рабочей папке сессии, а не в репозитории:
они привязаны к поднятому стенду и адресу туннеля.

Что проверяется только так:

* горизонтальный выезд страницы — 29 страниц на ширинах 390 / 768 / 1440 / 1920;
* 500-е и ошибки выполнения на всех маршрутах, включая карточки и админку;
* права по ролям: под каждой из четырёх ролей — состав меню, прямые ссылки на
  закрытые разделы, наличие плитки «Выручка»;
* раскрой: где физически встала деталь, повернулась ли она, что показывает блок
  «Что заказать поставщику».

Так же ловятся ошибки, которых не видит ни один линтер: серверный компонент,
передающий функцию в клиентский, компилируется и проходит проверку типов, а
страница падает с 500 при первой же отрисовке — этот случай в проекте уже был.

Адреса для обхода берутся из дерева `frontend/app/`, а не по памяти: половина
«очевидных» путей здесь называется иначе — раскрой плёнки живёт на
`/film-cutting`, прайс на `/admin/price-book`. Список, набранный на глаз, даёт
пачку 404 и создаёт видимость поломки.

### Оговорённое исключение: печатные страницы

Три страницы выезжают вбок на узком экране, и это правильно: бланк заявки
(`/leads/[id]/blank`), карта раскроя (`/leads/[id]/cutting`) и печатный отчёт
(`/reports/print`) свёрстаны листом A4 — `max-w-[210mm]`, это 794 px. На окне
390 px выезд ровно 404 px, на 768 — ровно 26 px: и то и другое равно
`794 − ширина окна`, то есть за край выходит сам лист, а не съехавший элемент.

Ужать лист под телефон — значит сломать печать, ради которой страница и
существует. Открывают её с компьютера, чтобы отправить на принтер. Остальные 26
страниц не едут вбок ни на одной из четырёх ширин.

## Чего пока нет

* Тестов компонентов с рендером: нужен jsdom и testing-library. Пока правила,
  которые стоит проверять, выносятся в чистые функции.
* Автоматического прогона браузером в общем наборе: скрипты требуют поднятого
  стенда, и запускаются руками.
