# ADR 0001: Modular Monolith

## Статус

Принято.

## Контекст

Нужен production-minded старт для системы автоматизации мебельного/фасадного производства с большим количеством доменов:

- intake и messaging adapters
- клиенты и CRM-поток
- заказы и статусы
- шаблоны изделий
- генерация деталей
- pricing
- production export
- stock
- audit

Сразу выделять набор микросервисов для такого старта нецелесообразно:

- возрастет сложность развёртывания
- усложнится трассировка доменной логики
- увеличатся накладные расходы на согласование контрактов

## Решение

Выбран модульный монолит:

- один backend runtime
- одна БД
- явные доменные пакеты
- отдельные сервисы и роуты по модулям
- минимальный shared layer

## Последствия

Плюсы:

- быстрый и контролируемый старт
- меньше эксплуатационной сложности
- проще обеспечивать транзакционную целостность
- легче развивать бизнес-логику вокруг заказа

Минусы:

- требуется дисциплина в соблюдении доменных границ
- со временем возможен рост связности между модулями

## Правило на будущее

Если отдельный модуль начнет:

- иметь независимый жизненный цикл релизов
- требовать отдельных SLA
- выполнять тяжелые фоновые задачи
- иметь собственную модель масштабирования

тогда он становится кандидатом на выделение в отдельный сервис.
