      плитки, см. выше); саму модель статусов заявки менять не стал —
      непонятно, что именно должно означать «в расчёте» для заявки: «в
      работе» (такой статус уже есть) или новый статус. Нужен ответ заказчика
- [x] «Вложения перепроверь, чтобы корректно отображалось». Карточка заявки
      печатала вложение как сырой служебный путь в хранилище текстом —
      открыть файл было нельзя в принципе, эндпоинта скачивания не было
      вовсе. Добавлен `GET /leads/attachments/{id}/download` (тот же
      контракт, что и у файлов заказа) и нормальный вид: миниатюра для фото,
      кнопка «Скачать»
- [x] «Диалоги убрать». Пункт скрыт из левого меню и с «Рабочего места» (там
      была отдельная кнопка-ссылка). Сам раздел и API не трогали — запись в
      меню не удалена целиком, а помечена `hidden`, иначе пропала бы проверка
      прав на прямую ссылку `/inbox`
- [x] «Номер — чтобы дважды не заносили предыдущие номера». Добавлен
      предпросмотр следующего номера заявки (`GET /leads/next-number`,
      честно совпадает с тем, что реально проставится при сохранении) —
      показывается подсказкой на «Рабочем месте» и на `/leads`. Само поле
      остаётся необязательным, как и раньше
- [x] Новый клиент с «Рабочего места» при отсутствии в базе — **уже
      сохранялся** и до этого раунда, отдельно перепроверено

### Итого

Из примерно 30 разобранных пунктов раунда: **сделано и проверено** — все,
кроме четырёх пунктов ниже; **уже было сделано раньше** (проверено и явно

## 11. Третий раунд — с новыми скриншотами

Пришёл со скриншотами того же дня: часть пунктов повторяет второй раунд под
другим углом, часть — новые находки по факту использования.

- [x] «ФРЕЗЕРОВКА = АРТИКУЛ, убери лишнее артикул». На скриншоте — таблица
      заявки на «Рабочем месте» (`lead-parts-table.tsx`), которую во втором
      раунде не трогал: слияние тогда сделал только в смете заказа. Теперь
      то же самое и здесь — графы «Фрезеровка» и «Артикул» слиты в одну,
      колонка «Артикул» убрана
- [x] «Цена не подтягивается, должна фиксироваться при первом создании
      нового артикула — сохраняется в справочнике и оттуда тянется». Реальный
      баг в моём же слиянии колонок: новая объединённая графа в смете заказа
      помечала несовпавшую строку `isCustom: true`, а сервер заводит новый
      артикул в справочник (`_adopt_new_article`) только когда `is_custom`
      **не** установлен. Строка с новым числовым артикулом и ценой раньше
      сохранялась «в одну эту строку» и не запоминалась — при следующем вводе
      того же номера цену приходилось набирать заново. Починено, проверено
      живым запросом через API: артикул «911» с ценой сохранился в
      справочнике сразу при первом сохранении сметы
- [x] «Доп. заказы должны быть видны только по кнопке "раскрыть"». Список под
      карточкой родителя свёрнут в `<details>`, по умолчанию закрыт
- [x] «Буквы к номерам заказа по направлению» (капсом). Разобрал отдельным
      сквозным аудитом с прогоном по реальной базе: **это не баг** — буква
      берётся из `number_suffix` направления, направления заведены верно
      (проверено в `backend/app.db` напрямую), заказы без буквы — это либо
      номер, вписанный менеджером вручную (буква тогда намеренно не
      добавляется — так решил сам заказчик раньше), либо доп.заказ,
      наследующий номер родителя как есть, либо направление у заявки не было
      выбрано вовсе. Настоящий пробел, который аудит нашёл, — поправить
      `number_suffix` можно было только через Swagger или прямо в базе:
      страницы в интерфейсе не было. Завёл `/admin/directions`
- [x] «Заказан материал добавь в список заказов, оплата, фильтр по сроку
      (сортировка), поиск по номеру заявки/ФИО». Материал и поиск (по номеру,
      клиенту, организации, комментарию) — **уже были**, отдельно
      перепроверено. Добавлено: колонка «Оплата» (баланс уже приезжал в
      ответе списка, `to_read` считает его на каждую строку — просто фронт
      его не показывал), сортировка по клику на «Срок» (`sort_by=due_date`,
      `sort_dir=asc|desc`, у бэкенда этого параметра не было вовсе — добавлен
      с нуля в `OrderRepository.list_orders`)
- [x] «Красным помечать заказы, которые горят (2-3 дня)». Просрочка уже
      подсвечивалась (`isOverdue`); добавлена `isDueSoon` — тем же красным,
      но не жирным, чтобы не путать с уже случившейся просрочкой
- [x] «Смета заказа — сделай как в рабочем месте». Добавлена «Вставить
      списком» — тот же разбор текста (`parseSizeLines`), что и в форме
      приёма заявки, теперь и в смете заказа, и (тем же компонентом) в форме
      создания допа
- [x] «Раскрой: эмаль и всё остальное — только МДФ; плёнка — МДФ И плёнка».
      Раньше три одинаковые кнопки «Открыть раскрой» на карточке заказа вели
      в один и тот же экран без различения типа. Теперь одна карточка
      «Раскрой заказа»: кнопка «Раскрой МДФ» всегда, «Раскрой плёнки» —
      только если в смете есть позиции `kind="film"`; обе несут готовый выбор
      типа работы (`/film-cutting?orderId=...&type=cutting|film`) — менеджеру
      не нужно переключать вручную. Тут же — скачать бланк и выгрузить CSV
      раскроя, без похода в «Технические действия»
- [x] «Перенеси блок раскроя, убери сгенерированные детали — или они для
      ЧПУ?». Да, для ЧПУ: `Part[]` строится из `order.items` (изделия
      каталога), не из сметы, и почти всегда пуст у заказов, ведущихся по
      смете. Убран из основного вида карточки — генерация (`generate-parts`)
      осталась в «Технических действиях», сам список `GET .../parts` на
      каждый заход карточки больше не запрашивается
- [x] «По клиентам больше инфы — последний заказ, баланс». Добавлены обе
      колонки, посчитаны одним пакетным запросом на всю страницу (не по
      клиенту — иначе полсотни клиентов дали бы полсотни лишних запросов).
      Заодно нашёлся настоящий баг вёрстки: у колонки «Почта» в шапке не было
      своей ячейки в строке — всё, что шло правее, было сдвинуто на одну
      колонку молча
- [x] «Чтобы с флешки на любой комп без настройки зависимостей». Собрана
      полностью самостоятельная версия: backend в embeddable Python (не
      editable-установка — настоящая, без зависимости от пути на диске
      разработчика), frontend в режиме `output: "standalone"` (Next.js сам
      упаковывает минимальный рантайм). `scripts/build-portable.ps1` +
      подробности и проверка переносом на другой путь — в
      [docs/portable-usb.md](portable-usb.md)

Все проверки после раунда снова зелёные: `pytest`, `ruff`, `black`,
`npm run typecheck`/`lint`/`test`, плюс отдельная сборка `npm run build` (в
изолированной копии — не в рабочей папке с запущенным dev-сервером, чтобы не
повторить инцидент с падением туннеля).

## Осознанный технический долг

### Фаза 1 (email-канал)

Принято сознательно, не является багом:

- **Нет retry с backoff для опроса.** Упавший опрос просто записывает ошибку и
  повторяется на следующем интервале. Для интервалов в минуты этого достаточно;
  dead-letter для стабильно неразбираемых писем — задача фазы 7.
- **`poll_cursor` пишется, но не используется как фильтр.** Дедупликация
  строится на `Message-ID`, что надёжнее UID (UID меняется при пересоздании
  папки). Курсор хранится для диагностики и для будущей оптимизации выборки.
- **Ответ отправляется только текстом.** Вложения в исходящих письмах не
  поддерживаются — inbox пока не даёт менеджеру прикреплять файлы.
- **Ошибка SMTP возвращает 502 и не ретраится автоматически.** Сообщение
  сохраняется со статусом `failed`, менеджер отправляет повторно вручную.
- **`rq` не импортируется на Windows** (fork-контекст multiprocessing). Обходится
  режимом `CHANNEL_POLL_INLINE=true`; в Docker/Linux используется обычный путь
  через очередь.
