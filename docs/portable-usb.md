# Портативный запуск с флешки

Заказчик: «чтобы я сегодня с флешки кинул это всё на комп и оно работало без
настройки зависимостей». Это отдельная, полностью самодостаточная сборка —
не тот же самый проект, а собранная из него один раз копия рантайма и кода.
Ставить Python, Node.js, Docker или что-либо ещё на целевой машине не нужно.

## Что это и почему не «просто скопировать `.venv` и `node_modules`»

Проверено прямо на этой машине: `backend/.venv` — это `pip install -e .`
(editable-установка). В `.venv/Lib/site-packages/__editable___fasad_backend_finder.py`
путь к исходникам зашит буквально: `C:\Users\...\OneDrive\Рабочий стол\fasad\backend\app`.
На любой другой машине, где нет точно такого пути, `import app` из этого
`.venv` не сработает вообще — даже если Python на ней тот же. Простое
копирование папки проекта такую сборку не переживает.

Портативная сборка устроена иначе:

* **backend** ставится в [embeddable Python](https://docs.python.org/3/using/windows.html#the-embeddable-package)
  (zip с python.org, без инсталлятора) обычной, **не editable** установкой
  (`pip install .`) — код физически копируется в `site-packages`, никаких
  внешних путей не остаётся;
* **frontend** собирается с `output: "standalone"` (`next.config.ts`) —
  Next.js сам упаковывает минимальный `node_modules` (65 МБ вместо 536 МБ
  обычного) в одну папку с `server.js`, который поднимается голым `node.exe`;
* **база** — та же SQLite, что и в обычной локальной разработке: файл
  `backend/app.db` рядом с кодом, ничего внешнего не поднимается.

Оба рантайма (`python.exe`, `node.exe`) не требуют установки — это и есть
смысл слова «embeddable»/«portable» в их официальных сборках. Проверено не
только на этой машине: собранная папка была скопирована на **другой путь**
(другая буква не проверялась физически, но оба рантайма официально не
привязаны к диску — привязка была ровно в editable-`.venv`, которую здесь не
используем) и запущена оттуда с той же базой — сервер и интерфейс поднялись
и отработали идентично, включая рендер страниц с реальными данными.

### Голая Windows: чего не хватает в самом embeddable-пакете Python

Проверено дополнительно — заказчик прямо спросил, заработает ли это на
«голой Windows» без единой ранее поставленной программы. Ответ был бы «нет»
без одной правки, которая уже внесена в `build-portable.ps1`.

Official embeddable-zip Python несёт `vcruntime140.dll`/`vcruntime140_1.dll`,
но **не несёт `msvcp140.dll` и `concrt140.dll`** — вторую половину VC++ 2015-2022
Redistributable. Часть колёс (`cryptography`, `bcrypt`, `psycopg-binary`,
`pydantic-core` — то есть буквально любая валидация запроса в FastAPI, а не
экзотика) собрана MSVC и тянет именно эти DLL. На машине разработки они
почти наверняка есть в `System32` — их туда ставит что угодно за долгие годы.
На действительно голой Windows их может не быть вовсе, и backend упал бы на
первом же `import cryptography` без единой строчки внятной ошибки в
консоли — просто «модуль не загрузился».

Решение — то же самое, что Microsoft официально называет «app-local
deployment» VC++ Runtime: положить `msvcp140.dll`/`concrt140.dll` рядом с
`python.exe`. Windows ищет DLL сначала в папке самого exe и только потом в
`System32` — с локальной копией результат не зависит от того, что стоит на
целевой машине. `build-portable.ps1` копирует эти DLL из `System32`
машины сборки автоматически на каждом прогоне, который качает Python заново;
если их вдруг нет и там — скрипт прямо предупредит в консоли, а не соберёт
тихо неработающую версию.

## Собрать

```powershell
cd H:\fasad
./scripts/build-portable.ps1
```

По умолчанию собирает в `..\fasad-portable` (рядом с проектом). Можно
указать своё место: `./scripts/build-portable.ps1 -Destination D:\fasad-usb`.

Первый прогон качает embeddable Python и portable Node.js из интернета
(нужен доступ в сеть на **машине сборки**, не на целевой) — около 40 МБ
суммарно. Повторные прогоны их уже не перекачивают, если папки `python/` и
`node/` на месте.

Результат — папка на **~300 МБ**:

```
fasad-portable/
├── python/        embeddable Python 3.12 + все зависимости backend
├── node/           portable Node.js 20 (только рантайм)
├── backend/        код + alembic + app.db (посеянная демо-база) + .env
├── frontend/        .next/standalone + статика + public
├── start.bat        двойной клик — поднимает всё и открывает браузер
├── stop.bat          останавливает
└── unblock.ps1       снимает блокировку Windows с файлов при каждом старте
```

`start.bat` перед каждым запуском сам снимает с файлов пометку Windows
«скачано из интернета» (`unblock.ps1`) — без этого перенос папки по сети или
флешке на другой компьютер иногда приводит к тому, что `node.exe`/`python.exe`
тихо блокируются SmartScreen без единой видимой ошибки.

Копируется на флешку целиком, `xcopy`/перетаскиванием — без исключений.

## Запустить на целевой машине

1. Скопировать папку `fasad-portable` куда угодно (флешка, `C:\`, `D:\` —
   без разницы, путь не зашит).
2. Двойной клик по `start.bat`.
3. Через несколько секунд откроется браузер на `http://127.0.0.1:3001`.
   Адрес для других компьютеров локальной сети напечатает `start.bat`.
4. Чтобы остановить — `stop.bat`, либо закрыть оба свёрнутых окна
   («Fasad — сервер», «Fasad — интерфейс»), которые открывает `start.bat`.

Требований к целевой машине: 64-битная Windows 10/11. Никакого Python,
Node.js и интернет на целевой машине не нужны — `start.bat` запускает уже
готовые `python.exe` и `node.exe` из соседних папок. Для первого доступа с
других ПК может потребоваться один раз запустить файл от администратора,
чтобы добавить правило брандмауэра на порт 3001.

Пока в демо-базе действуют стандартные пароли, интерфейс доступен только на
этом компьютере. Войдите локально, смените пароли всех перечисленных при
запуске пользователей в разделе «Администрирование → Пользователи» и снова
запустите `start.bat`. Тогда интерфейс откроется по сетевому адресу. Если порт
8000 или 3001 уже занят, запуск остановится с сообщением, вместо того чтобы
открыть чужое приложение.

## Лицензирование (привязка к компьютеру)

Портативная сборка привязана к одному компьютеру подписанным `license.key` —
подробно устройство и как выпустить лицензию для нового клиента описаны в
[`licensing/README.md`](../licensing/README.md), здесь только что видит
пользователь на месте.

Без `license.key` рядом с `backend\.env` сервер не поднимается вообще:
`start.bat` подождёт 30 секунд и покажет в своём окне последние строки лога
сервера, где будет отпечаток этого компьютера — его нужно прислать
разработчику, чтобы получить файл лицензии. Демо-стенды и разработка эту
проверку не видят — она включена только флагом `LICENSE_LOCK_ENABLED=true`,
который ставит сама портативная сборка.

## Из чего это не годится — осознанные ограничения

* **База — SQLite, для одного человека за одним компьютером одновременно.**
  Не для нескольких менеджеров в сети — под это существует обычная сборка
  (`docker-compose.yml`, PostgreSQL). Портативная версия — это демо-стенд и
  «показать клиенту прямо сейчас», не постоянное рабочее место команды.
* **RQ-очередь и email-опрос — по-прежнему через `CHANNEL_POLL_INLINE=true`**,
  тот же режим, что и на Windows в обычной локальной разработке (`rq`
  физически не импортируется на Windows, см. `docs/email-channel.md`).
* **Секреты (`JWT_SECRET_KEY`, `CHANNEL_SECRET_KEY`) генерируются один раз при
  сборке** и остаются в `backend/.env` внутри портативной папки — тот, у кого
  есть флешка, может прочитать `.env` как обычный текстовый файл. Для «показать
  демо» это нормально; для реального хранения чужих учётных данных каналов
  связи — нет. Не класть в эту сборку боевые пароли от чужой почты.
* Пересобирать (`build-portable.ps1`) нужно **после каждого изменения кода**:
  сборка — это снимок на момент запуска скрипта, не живая ссылка на проект.

## Если что-то не завелось

* `start.bat` пишет прямо в окне, чего не хватает (`python\python.exe`,
  `node\node.exe`) — значит, при копировании на флешку что-то не скопировалось
  целиком: проверьте, что папки `python` и `node` перенесены полностью.
* Сервер не поднялся за 30 секунд — `start.bat` сам печатает в своём окне
  последние строки `backend\server.log` (лог сервера пишется туда при каждом
  запуске) и не зависает бесконечно. Частые причины в этом логе:
  - нет `license.key` или он не для этого компьютера — см. «Лицензирование»
    выше, лог покажет отпечаток;
  - антивирус заблокировал `node.exe`/`python.exe` как «из интернета» —
    `unblock.ps1` снимает эту пометку сам при каждом запуске, но если антивирус
    успел карантинить файл раньше — снимите блокировку/исключение вручную.
* Порты заняты (`8000`/`3001`) — на целевой машине уже что-то слушает эти
  порты; поменяйте `BACKEND_PORT`/`FRONTEND_PORT` в начале `start.bat`.
